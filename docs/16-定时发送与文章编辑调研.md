# 16 定时发送与文章编辑：调研与方案

2026-10-31。状态：**0.12.0 已实现**（2026-11-01），做法见文末 §7；§5 的待拍板项已定：定时走 A 方案（增强原生弹窗，不调 X 接口），文章第一期做 Markdown 粘贴 / 导入、字数与阅读时长、大纲，放进福滤娃，推荐时段用自己主页数据。

## 1. 网页版现在哪里难用（2026-10-31 真机看过）

### 1.1 定时发送

- 入口在发帖框的日历图标，弹出「安排表」：月、日、年、时、分五个下拉框，加一个时区。每排一条都要从头点五个下拉框，默认值是「现在 + 几分钟」，不会记住上一次选的时间。
- 已排期的帖子藏在「草稿 › 预排期」里（`/compose/post/unsent/scheduled`），只有一个列表，没有日历视图，看不出哪天空着、哪天挤在一起。
- 只能一条一条排；串推（thread）、投票不能定时（多家文章都确认原生定时只支持单条帖子）。
- 没有「排期槽位」的概念：想每天 9:00、12:30、21:00 各发一条，只能自己记、自己算。

### 1.2 文章（X Articles，要 Premium；你的账号可用）

- 编辑器是 Draft.js，从别处粘贴过来常丢格式、段落合并、图片丢失；不支持 Markdown。
- 没有字数统计和阅读时长，没有大纲（长文里跳到某个小标题只能滚）。
- 代码块、表格支持差；图片要一张张手动传。

## 3. 定时发送：三种做法

|                 | A. 增强原生弹窗                                                          | B. 扩展直接调 X 内部接口排期                                                                                                                      | C. 扩展本地定时发                          |
| --------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| 怎么做          | 在 X 的「安排表」和发帖框里加按钮，替你填好五个下拉框，你点 X 的「确认」 | 扩展用你的登录态调 X 网页自己用的排期接口（`CreateScheduledTweet` 一类），自建排期界面                                                            | 内容存在本机，到点由扩展替你发             |
| 到点谁发        | X 服务器                                                                 | X 服务器                                                                                                                                          | 你的浏览器（电脑关了、浏览器关了就发不出） |
| 能批量排一周吗  | 不能，一条一条确认（但每条只要点两下）                                   | 能                                                                                                                                                | 能                                         |
| 串推 / 投票定时 | 不能                                                                     | 串推大概率不能（X 服务端也只收单条）                                                                                                              | 能                                         |
| 风险            | X 改页面就要跟着改选择器                                                 | 接口和 queryId 会变；扩展主动请求 X，和我们「不额外请求 X」的原则冲突（拉黑也是用户点了才发，可以按同样规则：只在你点了才发）；批量排期有风控风险 | 不可靠，会漏发；替用户自动发帖审核风险最高 |

**建议先做 A，再视情况补 B 的「批量」部分，不做 C。**

### 3.1 A 方案的功能

1. **排期槽位**：在面板设置你的发帖时间表，两种写法任选：
   - 固定时间点：如每天 9:00、12:30、21:00，可按工作日 / 周末分开；
   - 按间隔：如每天 8:00–23:00 之间每隔 3 小时一条。
2. **「下一个空档」**：在 X 的发帖框（日历图标旁）加一个按钮，一点就把下一个还没被占用的槽位填进 X 的安排表，你只要点 X 的「确认」。也放快捷键。
3. **快捷时间**：安排表里加 +1h / +3h / 明早 9 点 / 和上一条同一时间 等按钮；记住上次选的时间。
4. **已排期日历**：侧边栏新增「排期」视图，按天显示已排期的帖子和空着的槽位。数据来源：你打开 X 的预排期列表时，`xhr-bridge` 顺带读 X 已经返回的数据（不额外请求；接口名和字段开工时抓包确认，这次调研时预排期列表为空，没抓到）；「刷新」按钮可选做（会请求 X 一次，见 B）。
5. 「下一个空档」需要知道哪些时间已被占，用的就是第 4 条的数据；没同步过时按本机记下的「我通过扩展排过的时间」算。

### 3.2 B 方案（可选，第二步）

- 在侧边栏「排期」里直接写多条，一键按槽位全排上，到点由 X 服务器发。
- 带图片要先走 X 的媒体上传接口，工作量和风险都比 A 大一截。

## 4. 文章编辑增强

按价值排序，前三项建议第一期就做：

1. **Markdown 导入 / 粘贴**：在文章编辑器里粘贴 Markdown（或拖入 `.md`）自动转成 X 文章格式：标题、小标题、加粗 / 斜体 / 删除线、链接、列表、引用、分隔线、代码块；frontmatter 或第一个 H1 作标题。转换规则参考 xPoster（MIT）。
2. **字数与阅读时长**：编辑器角落常驻中文字数 / 英文词数 / 预计阅读分钟。
3. **大纲**：侧边栏显示小标题目录，点击跳转。
4. 图片：Markdown 里的本地图片按占位符逐张上传（参考 baoyu 的做法）；表格转图片。工作量大，放第二期。
5. 本机草稿自动备份和历史版本（X 编辑器崩了或误删能找回）。
6. 中文排版修正：中英文之间加空格、半角标点转全角等，一键整理。

## 5. 要你拍板的事

1. **定时先做 A（增强原生弹窗 + 槽位 + 下一个空档 + 排期日历）吗？** 要不要第二步做 B（侧边栏批量排期，会主动请求 X）？
2. **文章第一期做 Markdown 粘贴、字数、大纲**，可以吗？还有哪些你最常遇到的具体痛点？
3. **放在福滤娃里还是另出一个扩展？** 商店的「单一用途」现在写的是「改善 x.com 上的浏览」，加发帖和写作工具后要改成更宽的「X 刷推与创作副驾驶」，审核有被要求拆分的风险。放一起的好处是共用侧边栏、主页洞察（比如按你自己的帖子数据推荐发帖时段）。
4. 槽位时间表要不要用主页洞察里你自己的「发帖时段表现」自动推荐？

## 6. 不管选哪种都要守的规则

- 发帖、排期永远由你点最后一下（X 的「确认」/「发布」），扩展不替你发。
- 帖子内容和排期只存本机，不上传到 FeedSieve 服务器。
- 弹窗 / 侧边栏遵守界面规则：不写说明文字，说明收进 `!` 图标。
- 新增的数据处理同步写进 `PRIVACY.md` 和 08。

## 7. 实现记录（0.12.0）

代码在 `apps/extension/src/lib/compose/`，面板是 `entrypoints/popup/views/WriteView.tsx`（栏目「发帖」）。

| 文件                  | 内容                                                                                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `schedule-slots.ts`   | 发帖节奏设置、每小时容量、下一个空位、按主页热力图推荐时段（纯函数）                                                                                         |
| `scheduled-parse.ts`  | 解析 X 的 `FetchScheduledTweets` 响应和 `Create/Edit/DeleteScheduledTweet` 请求（纯函数，网络桥和内容脚本共用）                                              |
| `schedule-store.ts`   | 本机存储：`composeScheduleV1`（节奏）、`scheduledPostsV1`（已排期，按账号）、`scheduleAssignmentsV1`（待确认分配）、`scheduleLastPickV1`（上一次确认的时间） |
| `compose-schedule.ts` | 发帖框「排下一条」按钮、安排表快捷时间条、填 X 的下拉框、同步（让 X 打开预排期页）                                                                           |
| `markdown-article.ts` | Markdown → X 文章编辑器认的 HTML、字数统计（纯函数）                                                                                                         |
| `article-editor.ts`   | 拦下粘贴换成转换后的 HTML 交给 X 编辑器、标题填充、右下角大纲 / 字数面板、导入 .md                                                                           |

2026-10-31 / 11-01 真机实测（账号 @realchendahuang，测试数据已删除）：

- 安排表是五个原生 `<select>`（月 1–12、日、年（当年起 3 年）、时 0–23、分 0–59），中文界面 24 小时制；从内容脚本用原生 setter 写值再派发 `change`，X 能认，「将于 … 发布」跟着变。超过约一年（如 2028-11）X 不让确认。
- `CreateScheduledTweet` 请求体：`variables.post_tweet_request.status`、`variables.execute_at`（Unix 秒），响应 `data.tweet.rest_id`；`DeleteScheduledTweet` 请求体 `variables.scheduled_tweet_id`。`FetchScheduledTweets` 响应 `data.viewer.scheduled_tweet_list[]`。三条都已验证能被网络桥记下。
- 同步：`history.pushState` 到 `/compose/post/unsent/scheduled` 再派发 `popstate`，X 的路由会打开预排期弹窗并自己拉列表。
- 文章编辑器是 Draft.js（`[data-testid="composer"]`），标题是 `textarea[name="文章标题"]`。粘贴 HTML 只认 `<h2>`（副标题）、段落、`<strong>/<em>/<s>`、`<a>`、列表、`<blockquote>`（`<br>` 保留成换行）；`<h1>`、`<h3>`、`<pre>`、`<hr>` 都变普通段落。
- **坑**：粘贴后立刻把焦点移到标题框，Draft 会用粘贴前的内容覆盖回去，所以标题等 300 ms 再填。导入接在正文末尾时，先派发一次 Enter 起新段落，否则第一段会并进最后一段（插入空 `<p>` 不行，会被吞掉）。
- 已知限制：图片只能变成指向原图的链接（X 不收外链图片）；嵌套列表拍平；12 小时制界面（英文）按上午 / 下午下拉框处理，没有真机验证过。

### 7.1 第二轮（0.12.0 之后）

- 草稿队列：`schedule-store.ts` 的 `composeDraftsV1`；`compose-schedule.ts` 的 `COMPOSE_DRAFT_MESSAGE` 打开发帖框（`pushState` 到 `/compose/post` + `popstate`）、用合成 `paste` 贴正文（2026-11-01 实测 X 发帖框能接收，发帖按钮随之可用），再走「下一个空档」。网络桥记下 `CreateScheduledTweet` 后按正文前 280 字匹配并移除草稿。
- X 文章粘贴 `<h1>` 实测可用（之前以为不行，是因为粘贴的第一段会并进光标所在段、沿用那段的类型）。映射改为 `##` → h1（标题）、`###` → h2（副标题），和「复制为 Markdown」（`article-export.ts`，h1 → `##`、h2 → `###`）互为往返。
- 嵌套列表：X 把 `<ul><li>外<ul><li>内</li></ul></li></ul>` 的子项文字并进上一项，所以导入时拍平。
- 文章备份：`articleBackupsV1`，编辑停 5 秒后存，同一篇 10 分钟内覆盖最新版，每篇 5 版、最多 30 篇。
- 发帖框加了第二条以后（串推）`scheduleOption` 仍然可点，`CreateScheduledTweet` 的请求体里也有 `thread_tweets`，X 可能已经支持串推定时，没有真机验证。

### 7.2 给 AI Agent 的排版入口（2026-11-06）

- `skills/feedsieve-article/SKILL.md`：给外部 Agent（Claude Code / Codex / ZCode 等）的排版说明——在 ego-browser 里打开 X 文章编辑器、用原生粘贴把 Markdown 交给扩展自动转换、按「🖼 图片 N」占位符逐个插入本地图片、校验后把草稿留给用户。红线是只做草稿，不替用户点「发布」。
- `scripts/article-format.mjs`：纯转换 CLI（Node ≥22，直接复用 `markdown-article.ts`）：`node scripts/article-format.mjs article.md --html` 输出 X 编辑器认的 HTML，给没装扩展、或要先在本地预览转换结果的 Agent 用。
- 为什么先不做 MCP：真正难的是在已登录 X 的浏览器里操作 Draft.js，MCP server 得自己接 CDP / 浏览器（等于重造 ego-browser 的一半，还要持有登录态）；只把纯转换包成 MCP 工具价值又太薄（能跑 shell 的 Agent 直接调 CLI 就行）。先给 skill + CLI，等有只能走 MCP 的客户端再加一层薄封装。

## 8. 排期改成「发帖节奏」（0.13 开发中）

固定时间点 / 按间隔太像一张要用户自己维护的时间表，实际使用里用户只想：**我在哪些时段发、每小时最多几条、写完点一下排到下一条**。所以 0.13 把模型换成「节奏 → 容量 → 队列」：

| 层   | 做法                                                                                                                             |
| ---- | -------------------------------------------------------------------------------------------------------------------------------- |
| 节奏 | 设置 › 发帖辅助（发帖节奏区）：多段时段（每段可选星期 / 每小时最多 1–3 条）、随机分钟、最小间隔、最早提前量、最多提前 7/14/30 天 |
| 容量 | 按本地整点生成名额；`已用 = X 已排期 + 本机待确认`；重叠时段容量取最大 perHour，不会重复加名额                                   |
| 队列 | 发帖页按天显示每小时「已排 / 上限」；点有空位的小时，把队列里的下一条排进去；分配后分钟固定，可换一个                            |
| 确认 | 仍然只驱动 X 原生安排表，最后一下由用户点；本机分配在 `CreateScheduledTweet` / 预排期列表出现后清掉，避免两条草稿抢同一个小时    |
| 迁移 | 旧 `mode: times` 按整点合并成小时段，旧 `mode: interval` 换算成每小时条数；`composeScheduleV1` 键不变                            |

新增本机键 `scheduleAssignmentsV1`（分配：草稿 id、正文指纹、时间），未确认的占位 30 分钟后自动释放。随机只影响分钟，不影响小时；默认 1 条/小时，默认 4 个整点时段 = 每周 28 条，避免设置页一上来就给出「每天 20 条」的激进默认值。时段按整点设置，半小时窗口会被算成两个时钟小时的名额。
